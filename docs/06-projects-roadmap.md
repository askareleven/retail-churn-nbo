# 06 · Роадмап проектов: от первого проекта до самостоятельного ML Engineer

**Принцип:** каждый проект — это полный цикл (данные → модель → метрики → сервис → тесты → README), как в `00–05`. Каждый следующий проект добавляет **один-два новых класса задач** и **новые инструменты**, а не повторяет старое.
**Темп:** ~1–2 месяца на проект при работе параллельно с основной работой. Весь путь ≈ 14–18 месяцев.
**Критерий «могу сам»:** по новой задаче ты без подсказок выбираешь метрику, baseline, схему валидации, способ деплоя и можешь объяснить, почему.

**Обозначения:** 🟦 **ML** — классическое машинное обучение (линейные модели, деревья, бустинг, статистика); 🟪 **DL** — глубокое обучение (нейросети, PyTorch); ⚙️ **MLOps** — инженерия вокруг модели (деплой, мониторинг, автоматизация).
**Порядок:** сначала проекты 1–4 (только ML, фундамент). DL начинается с проекта 5. Проекты 9–10 про инженерию, а не про модели.

## Проект 1 · Churn & NBO на данных H&M ← текущий  `🟦 ML`
- **Что:** предсказание оттока + рекомендация следующего товара.
- **Датасет:** *H&M Personalized Fashion Recommendations* (Kaggle): ≈31 млн транзакций, таблицы `transactions`, `customers`, `articles`. Скачивание через Kaggle API после принятия правил соревнования.
- **Модели:** 🟦 Logistic Regression, 🟦 деревья, 🟦 случайный лес, 🟦 LightGBM.
- **Метрики:** ROC-AUC, PR-AUC, precision@k, MAP@12.
- **Стек:** ClickHouse, pandas, scikit-learn, MLflow, FastAPI, Docker, pytest, GitHub Actions.
- **Чему учит:** весь цикл табличного ML, валидация по времени, утечки данных.

## Проект 2 · Прогноз спроса (временные ряды)  `🟦 ML`
- **Что:** прогноз продаж по магазинам и товарам на 28 дней (M5 Walmart или Store Item Demand).
- **Датасет:** *M5 Forecasting – Accuracy* (Kaggle, Walmart): ≈43 тыс. рядов товар×магазин за ~5 лет, с ценами и календарём. Для быстрой отладки сначала *Store Item Demand Forecasting* (Kaggle): 50 товаров × 10 магазинов.
- **Модели:** 🟦 наивные baseline, 🟦 ARIMA/ETS (statsmodels), 🟦 Prophet, 🟦 LightGBM на лагах и скользящих окнах.
- **Метрики:** MAE, RMSE, WAPE, SMAPE; бэктест со скользящим окном.
- **Стек:** statsmodels, Prophet, sktime или darts, оркестрация Prefect.
- **Чему учит:** временные ряды, сезонность, иерархические прогнозы, расписание обучения. Ближе всего к твоему опыту в ритейле.

## Проект 3 · Кредитный скоринг и фрод (банковский)  `🟦 ML`
- **Что:** вероятность дефолта (Home Credit Default Risk) и/или фрод-детекция (IEEE-CIS).
- **Датасет:** *Home Credit Default Risk* (Kaggle): ≈300 тыс. заявок + связанные таблицы (кредитное бюро, платежи). Для фрода по желанию *IEEE-CIS Fraud Detection* (Kaggle).
- **Модели:** 🟦 логистическая регрессия со скоркартой (WOE/IV), 🟦 LightGBM/CatBoost, 🟦 калибровка вероятностей.
- **Метрики:** Gini, KS, PR-AUC, Brier score, калибровочная кривая, экономическая метрика (стоимость ошибок).
- **Стек:** CatBoost, SHAP, imbalanced-learn, optuna.
- **Чему учит:** сильный дисбаланс классов, интерпретируемость, калибровка, регуляторные требования. Прямо пригодится в банке.

## Проект 4 · Uplift-моделирование и A/B-тесты  `🟦 ML`
- **Что:** кому стоит отправлять акцию, чтобы она реально повлияла на покупку (датасет Criteo Uplift или X5 RetailHero).
- **Датасет:** сначала маленький *Hillstrom Email Marketing* (≈64 тыс. строк, есть в `scikit-uplift`), затем *Criteo Uplift Modeling* (≈14 млн строк). Альтернатива: *X5 RetailHero* (тоже в `scikit-uplift`).
- **Модели:** 🟦 S-/T-learner, 🟦 uplift-деревья, 🟦 causal forest.
- **Метрики:** Qini, uplift@k, AUUC; статистические тесты, мощность, MDE.
- **Стек:** scikit-uplift, causalml, scipy, statsmodels.
- **Чему учит:** причинность против корреляции, дизайн экспериментов. Продолжение твоего маркетингового опыта.

## Проект 5 · Рекомендательная система v2  `🟦 ML + 🟪 DL`
- **Что:** двухэтапная система «кандидаты + ранжирование» на MovieLens или Retailrocket.
- **Датасет:** сначала *MovieLens 1M* (для отладки), затем *Retailrocket* (Kaggle): события просмотр/корзина/покупка в интернет-магазине, ближе к ритейлу.
- **Модели:** 🟦 ALS (implicit), 🟦 LightFM, 🟪 двухбашенная нейросеть (two-tower), 🟦 CatBoost-ранкер.
- **Метрики:** Recall@k, NDCG@k, MAP, coverage, novelty.
- **Стек:** implicit, PyTorch, FAISS (векторный поиск), Redis.
- **Чему учит:** эмбеддинги, поиск ближайших соседей, оффлайн против онлайн-метрик.

## Проект 6 · Компьютерное зрение  `🟪 DL`
- **Что:** классификация изображений и затем детекция объектов (например, дефекты, товары на полке).
- **Датасет:** разминка на *Fashion-MNIST*; основной — *NEU Surface Defect Database* (≈1800 снимков, 6 типов дефектов, есть разметка для детекции, влезает в Colab). Вариант покрупнее: *SKU-110K* (товары на полках).
- **Модели:** 🟪 CNN с нуля → 🟪 transfer learning (ResNet, EfficientNet) → 🟪 YOLO.
- **Метрики:** accuracy, F1, confusion matrix, mAP, IoU.
- **Стек:** PyTorch, torchvision, albumentations, Grad-CAM, ONNX, TensorBoard/W&B.
- **Чему учит:** нейросети, аугментации, обучение на GPU (Colab/Kaggle), экспорт модели.

## Проект 7 · NLP: от TF-IDF до трансформеров  `🟦 ML → 🟪 DL`
- **Что:** классификация отзывов или обращений на русском/казахском языке.
- **Датасет:** *RuReviews* (≈90 тыс. отзывов на женскую одежду, тональность, GitHub/Kaggle). Для казахского языка по желанию *KazSAnDRA* (проверь актуальную ссылку на Hugging Face).
- **Модели:** 🟦 TF-IDF + линейная модель, 🟪 эмбеддинги, 🟪 дообучение BERT (RuBERT, multilingual).
- **Метрики:** F1 (macro/micro), precision/recall по классам, ошибки на примерах.
- **Стек:** Hugging Face (transformers, datasets), PyTorch, sentence-transformers.
- **Чему учит:** текст, токенизация, fine-tuning, сравнение простого и сложного подходов.

## Проект 8 · LLM и RAG-сервис  `🟪 DL (LLM)`
- **Что:** вопросы-ответы по документам (регламенты, база знаний) с ссылками на источники.
- **Датасет:** открытые тексты законов с *adilet.zan.kz* (например, о банках и банковской деятельности, о платёжных системах) + 50–100 вопросов с эталонными ответами, которые ты составишь сам. Внутренние документы банка использовать нельзя: они конфиденциальны.
- **Подходы:** чанкинг, 🟪 эмбеддинги, поиск, 🟪 переранжирование, промпт-инжиниринг, 🟪 лёгкое дообучение (LoRA).
- **Метрики:** recall@k для поиска, faithfulness и relevance ответа (RAGAS), ручная оценка.
- **Стек:** Qdrant или pgvector, LangChain/LlamaIndex (или свой минимальный код), FastAPI, API LLM.
- **Чему учит:** современный GenAI-стек, оценка качества генерации, защита от галлюцинаций.

## Проект 9 · MLOps-платформа (переделать Проект 1 «как в продакшене»)  `⚙️ MLOps`
- **Что:** автоматическое переобучение, версии данных и моделей, мониторинг.
- **Датасет:** тот же *H&M* из Проекта 1. Дрейф моделируем сами: обучаем на ранних месяцах, «поток новых данных» подаём по неделям из поздних.
- **Компоненты:** DVC (версии данных), Airflow или Prefect, MLflow Model Registry, Feast (feature store, по желанию), Evidently (дрейф данных и качества), алерты.
- **Метрики:** дрейф признаков (PSI), деградация метрик модели, время ответа, доля ошибок.
- **Стек:** Docker Compose → основы Kubernetes, облако (Yandex Cloud или AWS), Terraform по желанию.
- **Чему учит:** то, что отличает ML Engineer от Data Scientist: воспроизводимость, автоматизация, наблюдаемость.

## Проект 10 · Высоконагруженный inference  `⚙️ MLOps (+ 🟪 DL-оптимизация)`
- **Что:** сервис, который держит нагрузку и низкую задержку (рекомендации или скоринг в реальном времени).
- **Датасет:** модели из Проектов 1 и 5 (*H&M*, *MovieLens/Retailrocket*). Нагрузочные запросы генерируем из реальных id клиентов; отдельный датасет не нужен.
- **Подходы:** ONNX Runtime, батчинг запросов, кэширование, асинхронный FastAPI, потоки событий.
- **Метрики:** latency p50/p95/p99, RPS, потребление памяти, стоимость запроса.
- **Стек:** Kafka или Redis Streams, Redis, Locust (нагрузочные тесты), Prometheus + Grafana.
- **Чему учит:** производительность, нагрузочное тестирование, мониторинг сервиса.

## Проект 11 · Финал: Kaggle и воспроизведение статьи  `🟦 ML (+ чтение статей)`
- **Kaggle:** соревнование с табличными данными, цель — топ 20%. Учит ансамбли, стекинг, жёсткую валидацию.
- **Датасет:** Kaggle: актуальный *Tabular Playground Series* или другое табличное соревнование, которое идёт в момент старта. Статья: берём ту, у которой открытые данные и код-референс.
- **Статья:** воспроизвести результат одной научной работы по выбору (код + отчёт). Учит читать research и проверять заявленное.
- **Бонус:** вклад в open source (даже исправление документации к sklearn/mlflow).

## ML и DL: что к чему
| Тип | Проекты | Когда выбирать |
|---|---|---|
| 🟦 ML | 1, 2, 3, 4, 11 | таблицы, мало данных, нужна интерпретируемость и скорость |
| 🟪 DL | 5 (часть), 6, 7, 8 | картинки, текст, звук, очень большие данные |
| ⚙️ MLOps | 9, 10 (и часть каждого проекта) | всегда, когда модель идёт в продакшен |
В банковском и ритейл-ML на таблицах чаще всего побеждает 🟦 бустинг, а не 🟪 нейросеть. Поэтому ML идёт первым и занимает больше проектов.

## Правила работы с датасетами
1. Большие датасеты хранить в `data/raw/` (в `.gitignore`), в репозитории только скрипт загрузки и описание полей.
2. Перед использованием читать лицензию и правила Kaggle (для соревнований нужно нажать «Join» и принять условия).
3. Для отладки всегда брать маленькую выборку, потом полный объём.
4. Данные работодателя (Mechta, банк) в портфолио не использовать.

## Что учить параллельно (без отдельного проекта)
- **Математика:** линейная алгебра, вероятность, статистика, производная и градиентный спуск. По одной теме в неделю, сразу применяя в проекте.
- **Программирование:** алгоритмы и структуры данных на уровне собеседований, ООП, чистый код, ревью чужого кода.
- **SQL:** оконные функции, оптимизация запросов (у тебя уже сильная база).
- **Linux, Git, Docker:** ежедневно.
- **System design для ML:** как спроектировать рекомендации, скоринг, антифрод на собеседовании.

## Правила прохождения
1. Новый проект начинается только после того, как предыдущий задокументирован и ты объяснил его своими словами.
2. В каждом проекте обязательно: baseline → улучшение → сравнение в MLflow → тесты → README с метриками.
3. Не переходи к проекту 8–10 без проектов 1–3: сначала фундамент, потом модные инструменты.
4. Порядок можно менять, но 1 → 2 → 3 лучше оставить: они дают самую нужную базу.
